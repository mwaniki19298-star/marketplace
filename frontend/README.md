# Marketplace — frontend (design system + UI shell)

React + TypeScript + Vite + Tailwind. This first build phase ships the
design system, the responsive app shell (desktop sidebar / mobile bottom
nav / top bar), and three real screens wired to mock data: **Home**,
**Browse**, and **Product detail**. See `STYLE_GUIDE.md` for the design
rationale and full token/component reference.

## Run locally

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Open http://localhost:5173. Resize the window (or use dev tools device
mode) to see the shell adapt — sidebar and top-bar search below 768px
collapse into the mobile bottom nav.

## Connect to backend (local development)

Follow these steps to run the Django backend and have the frontend proxy API calls to it during development.

- **Backend (Windows PowerShell)**:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python manage.py migrate
python manage.py runserver 8000
```

- **Backend (macOS / Linux / Git Bash)**:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python manage.py migrate
python manage.py runserver 8000
```

- **Frontend (same machine)**:

```bash
cd frontend
npm install
cp .env.example .env
# Ensure VITE_API_PROXY_TARGET in .env points to the backend (default http://localhost:8000)
npm run dev
```

The Vite dev server proxies requests under `/api` to the backend using `VITE_API_PROXY_TARGET`, so frontend code can call the API with the base path `/api` or use `import.meta.env.VITE_API_BASE_URL`.

## What's real vs. mocked right now

- All components, tokens, and layout are real production code.
- `src/data/mock.ts` stands in for the API — every page reads from it
  instead of `fetch`. Swapping to TanStack Query hooks against the Django
  API is the next phase and won't require touching any component in
  `src/components/`.
- Only three routes exist (`/`, `/browse`, `/products/:id`). Nav links to
  Sell, Saved, Profile, Messages, Notifications, and the seller dashboard
  are wired but not yet routed — that's Phase 2/3 per the product brief.

## Folder structure

```
src/
  components/
    ui/       # design-system primitives (Button, Card, Badge, ...)
    nav/      # Sidebar, BottomNav, TopBar
  layouts/    # AppShell
  pages/      # routed screens
  data/       # mock data (temporary, until API integration)
  types/      # shared domain types
  lib/        # small utilities (cn, etc.)
```

## Cloudinary image uploads

The Sell page supports choosing images from the device and capturing photos on mobile. Images are uploaded directly to Cloudinary using a short-lived signature generated by Django; the Cloudinary API secret is never exposed to the browser.

Configure these backend environment variables:

```env
CLOUDINARY_CLOUD_NAME=your-cloud-name
CLOUDINARY_API_KEY=your-api-key
CLOUDINARY_API_SECRET=your-api-secret
```

The frontend requests `/api/media/cloudinary/sign/`, uploads images to Cloudinary, and sends the resulting `secure_url` values with the listing request.
